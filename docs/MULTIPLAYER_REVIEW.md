## What each acceptance layer means

The six Editor gates passed **54/24/29/27/22/20** on clean `eb51b22`, with zero failed checks or nested errors. The reliability suite uses real sockets inside one Editor process; snapshot fixtures include synthetic states. Neither constitutes independent native multiplayer acceptance. Matching builds and logs are retained under `artifacts/unity-validation/release-eb51b22-20261025T233739Z/`.

`tools/native_server_acceptance.py` runs the actual Linux dedicated server with two Python protocol clients and isolated temporary data. It passed **73 plain / 80 TLS checks**, including gameplay values, original native persistence failures, partial choices, idle/reconnect, retry and controlled restart. The final 30 native process logs contained no unexpected application exceptions. Python clients are not Unity GUI clients; earlier diagnostic runs that excluded failures are not the final verdicts.

Two standalone Linux Unity GUI processes passed **77 expected-versus-actual checks**, exercising the production transport, bootstrap, command router and presentation independently. Both replicas observed a potion restoring ally Health **4→8** with one potion/Action spent; two attacks dealt **3** damage each and spent one Action each; movement charged one Action. A new client process retained its Hero ownership. After an actual server restart, both clients accepted the new instance, reconnected and charged a subsequent move exactly once. During **36.0004 s** idle, the clients advanced **78/80** frames with fresh observations and exactly **0** camera drift. Reviewed real PNGs show the village and standing Heroes in both windows after restart.

`native-gui-tls-final-01/{results.json,visual-review.json,README.md}` and its two desktop PNGs beneath the evidence directory preserve the detailed bounded result. The development-only driver is confirmed absent from shipping Windows/server assemblies. See [native client acceptance](NATIVE_CLIENT_ACCEPTANCE.md) for its procedure. The Windows build compiled successfully, but Windows GUI execution and audio output remain unvalidated here; the Linux host reported no audio device at native FMOD startup. Linux graphical checks do not establish either result or certify all menus/cards/full visual UX.

Runtime source and tooling are pinned to `eb51b2292cf433a2cbe5dabb4863f1fef993161a`. Build provenance reports a clean worktree, unchanged application inputs and Unity **6000.6.5f1**. Later documentation-only commits do not change that built source; use `RuntimeSourceRevision.json`, player provenance and complete manifests instead of assuming the latest document commit was compiled.

An isolated native canary on DigitalOcean is another gate, using the actual service user and temporary data without joining the production room. Deployment success requires verified backups and secure health against the activated service. Friends connecting from real Windows machines adds the remote-client proof. None of these layers alone is a comprehensive mechanics audit or security certification.
